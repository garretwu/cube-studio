# Demo A: vLLM P95 Latency 灰度发布演示设计

## 1. Demo 目标

这个 Demo 的目标不是单纯展示“修复成功”，而是让观众清楚看到：

- 系统先识别到 `vLLM P95 latency` 异常。
- 系统先做诊断，再生成修复方案。
- 修复不是“一把梭全量执行”，而是先对小范围目标做 canary 验证。
- Canary 验证通过后，才继续扩展；如果回归，立即回滚。
- 前端要能完整回放故障上报、诊断、灰度执行、观察和最终结果。

## 2. 演示故事线

### 故事主线

1. `load_simulator` 持续打推理压力，建立稳定基线。
2. `fault_injector` 注入单一 GPU 争用故障，例如 `gpu-burn`。
3. Prometheus 触发 `VLLMLatencyP95High` 告警。
4. 前端告警页出现新事件，点击进入诊断会话。
5. 诊断 Agent 通过只读工具确认根因为 GPU 争用，给出高置信度修复计划。
6. 修复页展示 canary 计划，只对受影响目标先做最小范围修复。
7. Canary 成功后再扩展到完整范围，最终完成修复并写入记忆。

### 观众要感知到的重点

- 系统不是直接全量执行修复。
- 系统在修复前有明确的审批和可回滚记录。
- 系统会先观察小范围修复是否真的改善指标。
- 全量生效是验证通过后的结果，不是默认动作。

## 3. 故障与负载设计

### 负载侧

- 使用 `load_simulator` 持续施加 vLLM 推理压力。
- 负载要足够稳定，保证故障注入前后对比清晰。
- 演示窗口内维持 `P95` 在正常阈值附近，便于突出异常抬升。

### 故障侧

- 使用 `fault_injector` 注入单一 GPU 争用。
- 建议使用 `gpu-burn` 占用推理节点上的某张 GPU。
- 不引入第二根因，避免进入多候选诊断分支。

### 告警侧

- 以 `vllm_request_duration_seconds{quantile="0.95"} > 0.5` 作为主告警。
- 告警持续时间建议足够长，避免瞬时抖动影响演示。
- 告警触发后，前端应能立刻收到实时事件。

## 4. 前端观感设计

### 4.1 告警页

- 实时出现 `VLLMLatencyP95High` 卡片。
- 卡片里清楚显示：服务名、阈值、当前值、告警时间。
- 点击卡片后，跳转到诊断会话页。

### 4.2 诊断页

- 左侧展示 ThinkingTrace 时间线。
- 中间或右侧展示假设树和根因结论。
- 底部展示最终诊断卡片。
- 诊断结论要强调：`confirmed`，不是模糊猜测。
- 诊断结果里要能直接看到推荐修复方案。

### 4.3 修复页

- 修复页顶部首先展示 canary 卡片。
- 卡片里必须明确展示：
  - 当前批次
  - 目标范围
  - 观察窗口
  - 成功条件
- 不要把“全量修复”做成一开始就高亮的主按钮。
- 当 canary 通过后，再展示扩展到全量的状态切换。

### 4.4 结果页

- 展示修复前后 P95 对比。
- 展示 GPU util 下降、`gpu-burn` 消失、告警解除。
- 展示最终状态 `resolved`。
- 展示记忆系统更新结果。

## 5. 演示节奏

### 第一幕：告警出现

- `load_simulator` 已在运行。
- `fault_injector` 启动后，Prometheus 触发告警。
- 前端收到告警，用户进入会话页。

### 第二幕：诊断确认

- Agent 通过只读工具确认 `gpu-burn` 占用 GPU-0。
- 诊断结论要足够明确，让观众相信“系统知道问题在哪”。
- 此时不急着宣布修复成功，而是进入修复计划页。

### 第三幕：灰度修复

- 先对 canary 目标执行修复。
- 观众能看到一个小目标先被处理。
- 等待监控窗口，确认指标改善。
- 如果通过，再扩展到最终范围。

### 第四幕：完成与回放

- 最终状态变成 `resolved`。
- 前端展示完整时间线。
- 诊断和修复记录可回放。

## 6. 演示口播词

可以直接这样讲：

- “我们先不急着全量修复，先只对一个小范围目标做验证。”
- “如果这一步回归，系统会立即回滚。”
- “只有当观察窗口内指标稳定后，系统才会继续放大。”
- “这就是灰度发布的意义：先证明安全，再扩大影响面。”

## 7. 运行顺序

建议实际 demo 运行顺序如下：

1. 启动前端和后端。
2. 启动 `load_simulator`。
3. 等待 warmup。
4. 启动 `fault_injector` 的 GPU contention 场景。
5. 等待告警出现。
6. 打开告警页并进入诊断页。
7. 展示诊断过程和 canary 修复计划。
8. 执行 canary 修复。
9. 观察批次状态、指标变化和最终扩展结果。
10. 展示回放和记忆更新。

## 8. 成功标准

- 告警确实出现。
- 诊断结果是单根因高置信度。
- 修复计划包含 canary 配置。
- 前端能看到 canary 批次与观察窗口。
- 小范围修复通过后才继续扩展。
- 最终 P95 回落到阈值以下。
- 会话状态为 `resolved`。

## 9. 失败兜底

如果 demo 过程中 canary 没有按预期成功：

- 优先检查故障是否只注入了单一根因。
- 优先检查告警阈值是否过于保守。
- 优先检查 canary 事件是否已经进入前端。
- 必要时切换到 mock 模式，保留完整观感链路。

## 11. 与当前代码的差距

当前代码已经有 canary 骨架，但离完整演示还差以下几类能力：

- canary 批次事件粒度不够清晰。
- batch 作用域还没有真正体现在执行步骤中。
- LLM 生成的修复计划还没有稳定输出 canary 配置。
- 前端需要稳定收到 canary 生命周期事件，才能完整展示验证过程。

## 12. 结论

这个 Demo 的关键不是“修好一个 GPU 问题”，而是让观众看到：

- 系统先验证安全性。
- 系统再扩大执行范围。
- 系统失败可回滚。
- 系统最终可回放、可审计、可解释。
