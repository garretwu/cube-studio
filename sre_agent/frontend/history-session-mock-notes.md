# History Session Mock Notes

## 1. 目标

历史诊断页面用于查看已经结束的诊断会话。

设计原则：
- 先看结论，再看证据。
- 默认展示必要信息，不堆叠完整过程。
- 让用户在几秒内判断这次诊断发生了什么、影响了什么、最后怎么结束。

## 2. 页面定位

这是一个只读的历史回访页面，不是实时诊断页面。

页面重点回答 4 个问题：
- 这次诊断是什么问题。
- 影响了哪些对象和服务。
- 为什么得出这个结论。
- 最后是如何结束的。

## 3. 首屏最小信息集

首屏只展示以下内容：
- 会话标题
- 会话状态
- 开始时间
- 持续时长
- 根因摘要
- 影响范围
- 优先级
- 最终结果

要求：
- 用户进入页面后，不需要展开任何区域，就能理解这次历史诊断的核心结论。
- 不默认展示聊天记录。
- 不默认展示完整 trace JSON。

## 4. 信息结构

### 4.1 会话摘要

展示内容：
- session_id
- 标题
- 状态
- 开始时间
- 持续时长
- 是否发生过复诊

目标：
- 让用户快速确认这是一条什么历史记录。

### 4.2 诊断结论

展示内容：
- root_cause
- root_cause_layer
- root_cause_entities
- diagnosis_certainty
- confidence
- triage_priority

目标：
- 把最终诊断结论放在页面最核心的位置。

### 4.3 影响范围

展示内容：
- impact_summary
- affected_services
- 受影响对象数量
- 受影响服务数量

目标：
- 让用户快速知道这次问题影响面有多大。

### 4.4 关键证据

只展示少量高价值信息：
- 2 到 4 条关键 observation 或 hypothesis
- 每条只保留工具、时间、摘要、结果要点

要求：
- 默认摘要展示。
- 支持展开查看结构化字段。
- 不直接堆大段原始 JSON。

### 4.5 结束结果

展示内容：
- outcome
- 是否已恢复 / 已升级 / 失败
- 是否产出修复方案
- 是否执行过修复

目标：
- 让用户明确这次历史诊断最后停在什么状态。

## 5. 复诊场景

如果存在复诊，额外展示一块“复诊摘要”：
- 第几轮复诊
- 上一轮失败的候选根因
- 新增的关键证据
- 最终是否改判

要求：
- 没有复诊时，不展示这一块或直接折叠。
- 不展开完整 loop 过程，只展示回访必要信息。

## 6. 默认不展示的信息

第一版默认不放：
- 聊天输入框
- 实时 WebSocket 状态
- 全量消息历史
- 全量思维链回放
- 大段工具原始输出

原因：
- 这些更适合实时诊断，不适合历史回访首屏。

## 7. Mock 设计原则

历史页面的 mock 重点是“归档感”和“结论感”。

要求：
- 每条历史 session 都有明确结论。
- 首屏信息尽量结构化。
- 复杂过程压缩成摘要，而不是完整演示。
- 视觉上区别于实时诊断页，避免误认为还能继续诊断。

## 8. 第一版范围

第一版只需要支持：
- 历史 session 列表进入详情页
- 展示会话摘要
- 展示诊断结论
- 展示影响范围
- 展示关键证据摘要
- 展示结束结果
- 条件展示复诊摘要
